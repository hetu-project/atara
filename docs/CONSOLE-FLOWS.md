# Atara 控制台 · 流程与字段规格

> 公开版 · 2026-08-25
> 本文定义控制台里每一条流程走什么步骤、每一步填什么字段、按什么规则校验。
> 字段表列含义：`必填` Y=必填 / N=选填；`控件` text 文本 / pick 单选 / multi 多选 / date 日期 / upload 上传 / sign 签名 / auto 系统带出。

---

## 0. 全局规则

这四条约束所有流程，各流程不再重复：

| 规则 | 内容 |
|---|---|
| R1 一笔一工单 | 任何支付发起即建一条工单，有终态；终态后只读，不可续写 |
| R2 动钱必确认 | 每一笔资金流出都要过支付确认面板 + Passkey，无金额豁免 |
| R3 校验就地 | 校验失败不弹窗、不跳页，把错标在出错的那个字段上并聚焦它 |
| R4 前置拦截 | 后续环节必然失败的（无对手方、余额不足、低于最小单），在提交前拦下并给可点的替代 |

**四种终态**（互斥，全流程通用）：

| 终态 | 触发 | 资金 | 是否回写违约 |
|---|---|---|---|
| 完成 | 条件成立且放行共识通过 | 给收款方 | 正向回写 |
| 撤销 | 条件成立前主动撤 | 原路退回 | 不回写 |
| 超时 | 到期未履约 | 原路退回 | **负向回写** |
| 异议 | 窗口内提出异议 | 保持锁定 | 待裁决 |

## 1. F1 基础流程：进门 → 开户 → 第一笔

### 1.1 流程步骤

```
邀请码 → 注册 → 安全基线 → 身份认证(分段) → 入金 → 发起第一笔
```

### 1.2 S1 注册

| 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|
| 邀请码 | text | Y | 私有预览期校验；正式期取消 |
| 邮箱 | text | Y | 唯一；作为登录名与通知地址 |
| 手机 | text | N | 用于验证通知 |
| Passkey | sign | Y | 注册即绑定当前设备 |
| 支付密码 | text | Y | ≥4 位；两次输入一致 |
| ATR ID | auto | — | 系统生成，形如 `ATR-8F42C1`，**只读不可改**——单据与联系人引用的就是这个号 |

**规则**
- 支付密码不参与支付确认（支付走 Passkey），用途是：无 Passkey 设备时的退路 + 解锁会话
- 注册完成即可：浏览大厅、加联系人、收款。**不可**：付款、入金、挂单

### 1.3 S2 身份认证（分段触发）

不做一次性长表单，按**下一步需要什么**收：

| 段 | 触发条件 | 收集 | 解锁 |
|---|---|---|---|
| A | 注册时 | 见 S1 | 浏览、加联系人、收款 |
| B | 首次入金或首次付款 | 姓名、证件号、一个收款账户 | 入金、条件支付、小额成交 |
| C | 单笔 ≥ 阈值或申请商家 | 完整 KYC/KYB（见 §2.2） | 大额成交、公开挂单 |

### 1.4 S3 入金

| 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|
| 币种 | pick | Y | 取自资产列表 |
| 网络 | pick | Y | 随币种联动（USDT→TRON/ETH；USDC→POLYGON/ETH） |
| 充值地址 | auto | — | 按币种+网络生成专属地址，可复制 |

**规则**：跨链错转不可找回的告警必须与地址**同屏**，不放进帮助文档。

### 1.5 S4 出金（四步向导）

| 步 | 字段 | 控件 | 必填 | 校验规则 |
|---|---|---|---|---|
| 1 地址 | 收款地址 | pick | Y | 从白名单选；新地址登记后延时生效 |
| 2 金额 | 数量 | text | Y | `0 < 金额 ≤ 可用余额`；非数字/超额即标错 |
| 3 用途 | 用途 | pick | Y | OTC 结算 / 货款 / 服务费 / 退款 / 内部划转 / 其他 |
| 4 证明 | 证明文件 | upload | Y | 未上传不可提交 |

**规则**：四步逐步校验，当前步不通过不进下一步（`wdValid` 按 step 分支）。出金是唯一资金离开体系的口子，用途与证明在这一步收集成本最低。

## 2. F2 商家端：成为商家 → 挂单

### 2.1 三层结构

| 层 | 内容 | 变更频率 | 界面 |
|---|---|---|---|
| 账户级 | 资质（KYC/KYB） | 一次性 | 对话流长表单 |
| 能力级 | 经营配置 | 偶尔 | 对话流长表单 |
| 单笔级 | 挂单 | 每次 | 弹窗 |

**规则**：后一层的可选范围由前一层圈定。压平的后果是每次挂单都要重填经营配置。

### 2.2 S1 资质认证：先分流，再取字段

第 1 步选主体类型，之后走两条完全不同的路径：

| 主体类型 | 步数 | 路径 |
|---|---|---|
| Individual 个人 | 9 步 | KYC |
| Corporate 企业 | 10 步 | KYB |

**提交与回执规则**
- 提交后进入审核态，明确告知**预计一个工作日内**
- 回执由系统侧发出（用户没有"发送"动作，只有"查看"），可展开**全部已提交字段**分组呈现
- 审核通过后推送一条带入口的通知，直接进入挂单配置
- **新商户不预填任何履约数据**，履约率从零累计

### 2.3 S2 经营配置（能力级）

| 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|
| 交易方向 | pick | Y | 买入 / 卖出 / 双向 |
| 币种 | multi | Y | 从持仓币种中选 |
| 网络 | multi | Y | 随币种联动 |
| 单笔下限 / 上限 | text | Y | 下限 < 上限；上限受资质档位约束 |
| 收款通道 | multi | Y | 按地区分组（5 地区 / 22 条通道），就地展开不用浮层 |
| 定价方式 | pick | Y | 浮动（挂钩汇率）/ 固定 |
| 点差 | text | Y | 浮动定价时必填，默认 0.8% |
| 条款确认 | pick | Y | 必须勾选 |

### 2.4 S3 挂单（单笔级）

| 字段 | 控件 | 必填 | 校验规则 |
|---|---|---|---|
| 方向 | auto | — | 由能力级配置带出 |
| 币种 / 网络 | pick | Y | 范围由能力级圈定 |
| 结算法币 | pick | Y | 范围由收款通道圈定 |
| 单价 | text | Y | `> 0`；**按当时汇率与点差预填**，不让人从空白估价 |
| 数量 | text | Y | `> 0`；卖单额外要求 `≤ 该币种可用余额` |
| 最小单 | text | Y | `> 0` 且 `≤ 数量 × 单价` |

**规则**
- **挂出即锁币**：卖单提交后立即锁定对应数量，买家看到的可成交量必须真的在托管里
- 提交走支付确认 + Passkey（锁币是资金动作）
- **下架即解锁**

### 2.5 S4 履约

成交后商家侧动作：注资托管 → 等买家付款 → 确认到账。
**放款依据是银行凭证，不是商家的确认意愿。**

## 3. F3 买家端：发现 → 成交 → 付款

### 3.1 两条路径

| 路径 | 对手方来源 | 信任依据 | 章节 |
|---|---|---|---|
| 公开大厅 | 陌生人 | 信用模型 + 资质件 | §3.2 |
| 熟人网络 | 自己的联系人 | 关系 + 历史 | §4 |

### 3.2 S1 发现：挂单卡上必须有的字段

| 字段 | 为什么在列表上 |
|---|---|
| 信任分 | 选谁交易的第一判断依据 |
| 成交笔数 / 纠纷数 / 履约率 | 分数的来源，不能只给分不给依据 |
| 资质件徽标（KYC / PoF / 对账单 / PoA / SoW / 链上） | **缺件也公开**，让买家自己给缺口定价 |
| 单价 / 可成交量 / 最小单 | 最小单决定这条单跟我有没有关系 |
| 中位放行时长 | 履约速度是履约质量的一部分 |
| 结算法币 / 可用网络 | 不匹配的单不该浪费点击 |

**筛选字段**：方向（买/卖）、币种、结算法币。

### 3.3 S2 下单：核对卡

自然语言或动作面板生成的订单，提交前先核对：

| 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|
| 金额 | text | Y | `> 0`；按币或按法币两种口径 |
| 币种 | pick | Y | |
| 对手方 | pick | Y | 条件单必填；大厅成交时自动带出 |
| 结算法币 | pick | Y | 买卖单必填 |
| 用途 | pick/text | N | **选填**；系统从描述里推断，仅作备注，不影响资金 |
| 释放条件 | 组合 | N | 见 §3.5；空集 = 立即释放 |

**核对规则**
- 系统**推断**（非用户明说）的槽位标虚线；有虚线未确认就提交时，把问题标在问题上（变色 + 抖动），不弹解释
- 撮合必然失败的就地拦下：该币种/法币无对手方 → 给可选替代法币；低于最小单 → 给"改为最小单"的按钮

### 3.4 S3 支付确认（收银台）

每一笔动钱都出，四段固定：

| 段 | 内容 | 规则 |
|---|---|---|
| 金额 | 大字，货币符号与数字同级 | 唯一不能看错的信息 |
| 订单摘要 | 付给谁、为什么、释放条件 | 一句话 |
| 授权卡 | 周期已用/上限、单笔上限、收款白名单，本笔占用画在进度条上 | 超单笔上限即时标 `OVER CAP`；可切换其他卡 |
| 资金去向 | 法币：从名下哪个账户直付；数字资产：从可用余额锁进托管 | **陈述句，不是选择器** |

**规则**：底部按钮固定为 Passkey 确认。超对手方限额时，卡片下方多一行琥珀色原因说明。

### 3.5 释放条件的字段规格

条件 = **最多 3 个原子的 AND 组合**；空集 = 立即释放。不支持 OR（任一满足即放，等于对手方只需攻破最弱条件）。

| 原子 | 参数字段 | 控件 | 选项 / 规则 |
|---|---|---|---|
| **确认** Approval | 谁确认 | pick | 双方确认（默认）/ 我确认 |
| **凭证** Evidence | 凭证类型 | pick | 银行回执 / 交割单 / 工作成果 |
| **API 数据** Data | ① 数据源 | pick | 广告平台 / 物流 / 支付网关 / 链上预言机 |
| | ② 指标 | pick | **随数据源联动**（换源即重置指标） |
| | ③ 目标值 | text | 自由输入，如 `≥ 1,000` |
| **时间** Time | 日期 | date | 绝对日期 |

**超时兜底**（独立字段，不属于条件集）：默认 14 天未成立转人工审查。
**规则**：兜底不写进条件文本，在条件下方压一档小字单独说明，且只在单据仍可能悬着时显示。

### 3.6 S4 成交后状态机

| 阶段 | 状态标签 | 谁在动 | 超时后果 |
|---|---|---|---|
| match | Pending | 买方确认成交 | — |
| s1 | Waiting | 对手方注资托管 | — |
| s3 | **Your turn** | 买方转法币并回传回执 | **逾期判违约**（负向回写） |
| s4 | Verifying | 平台核验回执 | — |
| s5 | Done | 放款并回写履约 | — |

**规则**：`match` 与 `s3` 两态买方可主动撤单，记为未成交，**不记违约**——与逾期严格区分。

### 3.7 条件支付的执行轨道

轨道站名**跟真实条件类型走**，不跟内部编译分支走（等指标不是等日期）：

| 条件类型 | 轨道 |
|---|---|
| 立即 | 资金锁定 → 放行共识 → 已放款 |
| 双方确认 | 资金锁定 → 对方交付 → **你确认** → 放行共识 → 已放款 |
| 凭证 + 窗口 | 资金锁定 → 对方上传凭证 → **你的异议窗口** → 放行共识 → 已放款 |
| API 数据 | 资金锁定 → **等待指标达标** → 放行共识 → 已放款 |
| 时间 | 资金锁定 → 等待日期 → 放行共识 → 已放款 |

**规则**：每一站要写清"谁在等谁"；条件成立前，撤单入口一直可用。

## 4. F4 社交与交易网络

### 4.0 为什么熟人也要条件支付

既然是熟人，还要条件干什么？——**熟人场景下条件不是"因为不信你"，是"把口头约定变成可执行的"**。

生意上的熟人是纠纷高发区：供应商、承包商、长期合作方，金额大、周期长、约定多半口头（"下周发货""验收后付尾款"）。出问题不是不信任，是**没人记得当初说的哪个版本**。条件支付在这里的作用是把约定写下来自动执行，顺带把"催款"从伤感情的事变成系统行为。

推论：**熟人转账必须能带条件**，否则它只是一个更差的微信转账。

### 4.1 S1 添加联系人

| 方式 | 输入字段 | 规则 |
|---|---|---|
| ATR ID | ID（`ATR-XXXXXX`） | 精确匹配，不做模糊搜索（防撞库遍历） |
| 二维码 | 扫码 | 内容即 ATR ID |
| 邀请链接 | 手机/邮箱 | 对方注册后自动互为联系人——**增长主路径** |
| 从成交记录添加 | 选择一笔历史成交 | 把一次性对手方转为长期联系人 |

**添加请求字段**

| 字段 | 控件 | 必填 | 选项 / 规则 |
|---|---|---|---|
| 对方 ATR ID | text | Y | |
| 关系标签 | pick | Y | 供应商 / 客户 / 同事 / 朋友 / 我的另一个账户 |
| 备注名 | text | N | 仅自己可见 |
| 附言 | text | N | 随请求发给对方 |

**规则**
- **必须双向确认**：对方同意后才建立关系。单向可加等于开放骚扰面，而联系人直接关联收款关系
- 关系标签决定**默认条件模板**：供应商 → 凭证 + 我确认；客户 → 立即；朋友 → 立即
- 备注名只对自己生效，不影响对方展示

### 4.2 S2 联系人字段

| 字段 | 来源 | 对我可见 | 对对方可见 |
|---|---|---|---|
| 昵称 / 头像 | 对方 Profile | Y | — |
| ATR ID | 系统 | Y | — |
| 关系标签 | 我设置 | Y | **N** |
| 备注名 | 我设置 | Y | **N** |
| 与我的往来笔数 / 净额 | 系统累计 | Y | 各自看自己的 |
| 信任分 | 信用模型 | **默认隐藏**，见 4.4 | — |

### 4.3 S3 熟人转账

与大厅路径**共用同一套后端流程**，差别只在默认值与展示：

| 环节 | 大厅（陌生人） | 熟人 |
|---|---|---|
| 发起入口 | 大厅点单 | 联系人卡片 / 会话内直接发起 |
| 对手方 | 从公开挂单挑 | 已确定，跳过挑选 |
| 条件默认值 | 按场景预填 | **按关系标签预填** |
| 对手方评估 | 完整共识 + 结论长文 | 降级展示，见 4.4 |
| 收款信息 | 平台中转 | 直接用联系人已登记账户 |

**转账字段**

| 字段 | 控件 | 必填 | 规则 |
|---|---|---|---|
| 收款人 | auto | — | 从联系人带出 |
| 金额 / 币种 | text + pick | Y | `> 0` 且 `≤ 可用余额` |
| 释放条件 | 组合 | N | 默认值由关系标签决定；可改 |
| 用途 | pick/text | N | 备注性质 |

**规则**：会话内应能直接发起支付，订单卡贴进会话流——当前会话与支付是两条不通的路，这是最该补的一处。

### 4.4 熟人场景的信任展示规则

对陌生人展示信任分是**定价**；对熟人展示信任分是**冒犯**。

| 情形 | 展示 |
|---|---|
| 共识通过 | 只留一行"已通过 N 项检查"，**不展开分数** |
| 有异常或不通过 | **必须展开**，说清是哪一项（制裁命中、资金来源异常等） |

**规则**：共识照跑，合规筛查与资金溯源不因为是熟人而跳过。熟人关系不能成为风控静默的理由，但也不该把"给朋友转账"变成一次征信查询。

### 4.5 二度关系

| 字段 | 用途 |
|---|---|
| 共同联系人数量 | 与陌生对手方交易时的信任信号 |
| 关系路径 | 显示"你和他之间隔着谁"，而不是给一个不可解释的分数 |

**规则**：可见粒度未定。
