# Atara 条件支付 · 产品说明

> 公开版 · 2026-08-25
> 本文说明 Atara 做什么、一笔条件支付怎么走完、边界在哪。
> 内部另有工作稿维护假设、验证状态与未决事项，不在此文范围内。
> 信息分级：【事实】有数据或材料支持；【推断】由事实推出；【决策】当前做法。

## 1. 背景与问题

> 回答：要解决的问题是什么，为什么现在做。

**问题**：两方在缺乏信任基础时移动大额资金，总有一方需要先动，并在对方履约之前持续暴露于损失之中。现有支付体系保证钱能到账，不保证这笔钱该不该到——条件是否满足、违约如何处理，都在支付体系之外。

三个背景变化使这个问题值得现在做：

1. **执行层利润消失**【事实】。巴西 Pix、印度 UPI 提供免费即时转账，Pix 占巴西零售支付笔数 54.7%。转账动作本身不再产生利润。
2. **发行层利润消失**【事实】。2026 年 6 月，Visa、Stripe、BlackRock 等 140 余家机构发布 OUSD：零成本铸赎、储备收益返还合作方。稳定币发行的利润空间被主动压缩至零。
3. **agent 交易缺少争议机制**【事实 + 推断】。x402 协议清洗后的数据显示，链上原始流水约九成为测试与刷量，真实交易集中在交付即消耗、无需退款的商品（API、算力、token）（Artemis，2026-07）。由此推断：缺少争议机制的支付协议无法承载可能出错的商品，争议处理能力决定该市场可覆盖的范围。

结论：支付链条中「条件判定、违约定价、出错回滚」这一层（下称信任层）尚无成熟方案，需求随 agent 交易上升。本产品以这一层为目标位置。

## 2. 目标

> 回答：产品要达成什么，第一阶段以什么为准。

**产品目标**：让缺乏信任基础的两方能够完成大额交易。方式是把信任成本计算出来——逐笔评估对手方违约概率，按风险决定押金、费率和回滚安排，替代全额占用资金或依赖第三方担保。

**第一阶段目标**【决策】：

- 聚焦大额结算场景：OTC 换 U、换汇、贸易预付款
- 以托管形态运营：条件满足才放款，不承担损失，对外明确标注为服务费而非承保（依据见 §11）
- 积累两类数据：履约记录（信用模型的训练数据）与损失记录（后续承保定价的依据）

**主指标**：年化条件支付总金额。笔数、集成数与收入无直接对应关系，不作为主指标。

## 3. 用户与场景

> 回答：优先服务谁，为什么是他们。

当前更值得优先验证的用户，通常同时具备以下三个特征：

1. 单笔金额较大，失败或延迟带来的损失较高
2. 交易对手通常不是长期合作方，缺乏稳定信任关系
3. 现有支付渠道至少存在一种明显限制（额度、到账效率、实名要求或单据流程）

仅满足其中一项时，现有银行或 P2P 渠道通常仍可覆盖，暂不作为第一阶段重点。

【逻辑缺口】以上三特征由应用场景与从业者经验推出，尚未经过客户访谈验证。

| 客户类型 | 典型场景 | 优先级与理由 |
|---|---|---|
| U 商 / 做市商 | 高频大额出入 U，对手方常为陌生方 | ① 频次高，履约数据积累最快 |
| 交易所 | 大额撮合成交后的资金交割 | ② 当前唯一有明确意向的客户类型 |
| 出海企业财务 | 海外营收定期回流 | ② 单笔大，需求边界清晰 |
| 贸易进口商 | 向陌生供应商付预付款，单笔 5 万–100 万美元【事实：从业者经验】 | ③ 单笔最大，决策周期以季度计 |
| Agent 平台 | 为 agent 接入支付能力 | ④ 保留接口，待出现真实交易数据后重排 |

**C 端与个人**：暂不作为收入来源，因为单笔金额小，风险定价空间有限。其价值在于：高频交易沉淀履约数据（职业换汇商从该人群中产生），以及作为前台产品的用户基础。

**区域选择（摘要）**：优先资金枢纽（香港、阿联酋、新加坡），因为大额与 OTC 换手集中、监管路径明确；货币通胀市场（阿根廷、尼日利亚等）契合度高，但公开证据以零售口径为主，经访谈验证后进入。

## 4. 用户现有流程

> 回答：他们今天如何完成这类交易。

以两个优先场景为例。

**OTC 大额换 U（U 商、大额个人）**：通过熟人圈或中间人找到对手方 → 口头议价 → 由先付一方承担风险，或由中间人担保并收取佣金→ 金额较大时安排面交 → 交易完成后无正式单据。

**贸易预付款（进口商）**：与陌生供应商谈定条件 → 申请信用证（约四成企业申请被拒【事实：ADB 第 9 次全球调查】）或直接预付 → 预付后等待发货，期间无任何保障 → 出现纠纷依赖协商或诉讼。

两个流程的共同点：信任由关系和中间人提供（有佣金、不可规模化），或由先付一方单方面承担。

## 5. 核心痛点

> 回答：现有流程中，用户具体承担了什么问题。

按问题所处的环节分三类：

**资金安全**

- 先付一方承担全部违约风险：进口商付款后担心不发货，OTC 换手担心对方收款不放币
- 到账不等于交易结束：巴西 PIX 的 MED 机制可在到账后冻结追回资金，银行同样可事后冻结【事实：从业者经验】

**过程信息**

- 付款后资金位置、到账时间、最终被扣费用均不可见；行业层面无测算大额支付透明度的数据源【事实：FSB】

**渠道与合规**

- 合规通道限额低、对公开户周期长（香港 KYB 3–6 个月、涉加密业务拒户率高【事实：从业者经验】）、单据要求重
- 不走合规通道则面临账户与资金冻结

## 6. 现有替代方案及不足

> 回答：这些问题今天怎么被解决，为什么不够。

现有六类机制，共同点是都不对风险定价——信任成本被转嫁到本金、担保方或关系上，好对手方和坏对手方付出相同成本：

| 机制 | 谁在用 | 优势 | 不足 |
|---|---|---|---|
| 全额托管 / 预付 | 银行信用证、支付宝担保交易、Escrow.com；Skyfire、x402、ERC-8183 | 零风险，不需认识对方 | 100% 资金占用 |
| 事先设上限 | Kite、Google AP2、Coinbase AgentKit、Visa/Mastercard agent token | 简单，损失有顶 | 上限与对手方无关：低风险方被限制，高风险方批到上限 |
| 人工审批 | 银行大额审批、Catena | 能处理例外 | 慢，不可规模化，审批质量依赖个人判断 |
| 担保方承接 | Visa/Mastercard 拒付、保理、信用保险；本金台 | 体验好，即时确定 | 抽取价差，按关系定价，担保方是单点 |
| 熟人 / 声誉分 | OTC 关系网；币安、OKX 商家评级；ERC-8004 | 零成本，可携带 | 只反映相对好坏，无法回答能押多少钱 |
| 给风险定价 | ARS（论文阶段）、t54 ClawCredit（仅微额） | 可降低资金占用 | 需要真实违约数据，冷启动难；大额区间在已调研范围内无可用产品 |

两个补充事实说明传统信任供给在收缩：全球贸易融资缺口 2.5 万亿美元，中大型企业拒贷率 40%，与小企业几乎持平【事实：ADB】；将信用证流程搬上区块链的四个大型联盟（Contour、Marco Polo、TradeLens、we.trade）已于 2022–23 年全部停运【事实】。

## 7. 产品机会

> 回答：空位具体在哪，为什么我们有条件占据。

**空位位置**。以 agent 支付的分层为例（大额结算侧结构相同）：

| 层次 | 要解决的问题 | 现状 |
|---|---|---|
| 身份 | agent 是谁、归谁所有 | 已有多家提供 |
| 授权 | 谁批准花多少、超限如何处理 | Visa TAP、Google AP2 等均在建设 |
| 执行 | 钱怎么付 | x402、稳定币轨道，已成熟 |
| 履约与裁决 | 未交付如何处理、违约谁承担 | OKX Agent Payments Protocol（2026-04）提供托管与交付验证放款，争议解决未上线；风险定价（违约概率、保证金、保费）在已调研范围内仍无供给【事实：其官方文档核实】 |

**我们的条件**【推断】：风险定价依赖真实履约数据，该数据只能从真实结算中产生。结算业务先行，为信用模型提供其他进入者短期内无法获得的训练数据；裁决记录同时构成争议处理的判例积累。

**时间窗口**【事实 + 推断】：各金融中心稳定币牌照制度于 2025–26 年密集落地（香港首批 2026-04、阿联酋过渡期至 2026-09、美国不晚于 2027-01），法币出入金须经持牌机构成为长期约束；先建立持牌合作与合规运营记录的进入者获得结构性位置。

## 8. 产品方案

> 回答：我们具体提供什么能力。

### 8.1 架构

自底向上三层：

| 层 | 组成 | 职责 |
|---|---|---|
| 底层 | 结算链 | 条件原子结算：托管、验条件、放款、回滚在一次结算内完成 |
| 中层 | Atara 协议 + AIUSD | 协议判定条件是否成立，并为对手方定价；AIUSD 是携带条件的记账货币 |
| 前端 | Loka.cash | 人与 agent 的入口，用一句自然语言发起一笔条件支付 |

### 8.2 两项核心能力

- **裁决**：判定条件是否成立。回退规则在交易前公开，按确定性规则执行。
- **信用定价**：每笔支付前计算对手方违约概率，输出押金比例、费率与回滚安排。

裁决是定价的前提：违约概率需要一个中立的判定来源，否则定价没有落点。两者的数据关系：结算产生履约记录 → 记录训练信用模型 → 模型降低下一笔的押金要求。裁决的中立性决定数据质量。

### 8.3 AIUSD

协议的记账货币，品类为条件性稳定币：每笔转账携带生效条件，「到账」与「生效」为两个独立状态。资金进出走通用稳定币或法币轨道，条件与裁定结果在 AIUSD 账本内记录。现阶段以 USDT/USDC 托管形态运营，AIUSD 在取得发行牌照后上线【决策】。

### 8.4 B 端方案组装

基础能力不对外单卖，对外交付按「客户 × 场景 × 区域」组装的方案。风险定价与合规策略按走廊（出发国 × 落地国 × 落地方式）分层配置，不使用单一全局模型；合规采用规则模板与模型判断的双层结构【决策：采纳自外部桌面研究】。

| 能力 | 职责 |
|---|---|
| 条件托管 | 资金锁定，条件成立放款，不成立退回 |
| 裁决 | 条件判定（回执 / 单据 / 验收 / 读数）与争议处理 |
| 风险定价 | 违约概率 → 押金、费率、额度 |
| 验资合规 | KYC、钱包溯源、制裁筛查、审计单据包 |
| 出入金通道 | 各区域持牌伙伴的法币腿 |
| 双盲撮合 | 匹配对手方，双方互不暴露 |
| 计价记账 | AIUSD |
| 接入方式 | 对话前台 / API / SDK / 收款链接 |

| 方案 | 客户 × 区域 | 能力组合 |
|---|---|---|
| 交易所结算 | 交易所 × 资金枢纽 | 托管 + 裁决（回执）+ 风险定价 + 验资 |
| 贸易预付款保障 | 进口商 × 货币通胀市场 | 托管 + 裁决（单据）+ 风险定价 + 出入金通道 |
| 财资回流 | 出海企业 × 资金枢纽 | 出入金通道 + 验资 + 托管 + 单据包 |
| OTC 结算台 | U 商 × 资金枢纽 | 双盲撮合 + 托管 + 验资 |
| Agent 支付接入 | Agent 平台 | API + 风险定价 + 托管与回滚 |

### 8.5 技术架构：四层栈（官网口径，2026-08-24 上线）

> 本节按官网已公开发布的「The Atara Stack」文案回填，**不是新设计**。
> 主张：每一层各加一条保障，且每一层都对证据负责、不对我们负责（官网原话：You don't have to trust us）。
> 顺序即一笔交易的走向：**入口 → 判断 → 执行 → 沉淀**。

| 层 | 组件名（官网） | 职责 | 对外承诺的那一句 |
|---|---|---|---|
| 1 入口与路由 | Atara-pay | 一个接入面收下订单、额度与对账，并决定这笔在哪结算。API / SDK、API keys、按对手方分域 | 一把 key、一笔单；你不用挑链也不用挑场所 |
| 2 判断 | Aegean-consensus | **两个模型各判一次**：信用模型算对手方违约概率，裁决模型判条件是否成立。判定需 **M-of-N 签名**，并带上所依据证据的轨迹（Verdict proof） | 没有单一模型、也没有单一运营方能定你的案子 |
| 3 执行 | Loka-chain | 资金由合约持有，三态：hold / release / rollback，时限由区块时间强制而非由我们。合约部署在对手方本来就结算的那条链上，价值不跨链。另有 HTLC 通道做低延迟与争议兜底 | 我们所有服务都挂了，双方仍能各自取回；不走桥 |
| 4 沉淀 | 记录层 | 每笔结算写一行：谁付了、谁提了异议、最后怎么判；由结算本身写入而非任一方填报。行与导致它的事件之间连 **VLC 因果边**，另有 TEE 证明；信用模型下一笔读这些行 | 第二笔的价格由第一笔决定，依据是结算记录而不是自报的分数 |

底部另有两条横贯说明：**Final settlement**（自动 / 可审计 / 可追溯 / 我们宕机时仍可用）与 **Ecosystem**（多链部署、信誉可携带、开放 API）。

**与产品实现的对应**（本 PRD 已写的部分落在哪一层）：

- 第 2 层「两个模型各判一次」= §9.1 的两处共识：交易前对手方评估（信用模型）与放行共识（裁决模型，§9.1 第 6 步）。**M-of-N 签名正是当前 6/7、5/5 这类票数门槛的协议化表述**
- 第 3 层三态 hold / release / rollback = §9.0 四种终态里的「完成 / 撤销·超时·异议」的资金侧
- 第 4 层「结算写行、信用模型下一笔读它」= §10.6 兑现率的信号来源


## 9. 核心流程

> 回答：一笔交易如何从发起走到完成。

### 9.0 端到端用户链路

> 回答：一个用户从注册到查完历史订单，全程经过哪些环节；每个环节由 PRD 哪一节定义，原型做到了哪一步。

此前 PRD 只覆盖链路中段（提交订单到放款）。两端（开户、入金前置、安全基线、终态语义、历史查看）此前散落或缺失，本节补齐并作为索引【决策 2026-08-20】。

| # | 环节 | 内容 | 定义位置 | 原型状态 |
|---|---|---|---|---|
| 1 | 注册与账户认证 | 账户级 KYC（个人 9 步）/ KYB（企业 10 步），一次完成全平台复用；认证挂在账户不挂在单笔【决策】 | 本节；合规要求见 §10.7 | 已做（目前挂在「成为卖家」入口下，买家路径未单独引导） |
| 2 | 入金 | 专属充值地址 → 监听到账 → 溯源与地址聚类筛查；未通过隔离入补充材料流程，不直接退回 | §9.3 数字资产六步 1–2 | 已做（充值弹窗为示意） |
| 3 | 安全基线设置 | Passkey 注册、两步验证、支付密码（§9.4）、出金白名单（登记后延时生效） | 本节新增；出金部分见 §9.3 第 6 步 | 已做（Account → Security；Passkey 为仪式模拟，不采集任何真实凭据）。**2026-08-24 移除「强确认阈值」设置项**——分档取消后它无对象可设 |
| 4 | 发起 | 三入口：自然语言 / 动作面板 / 交易池。统一句法：在[X 条件]下，[A]向[B]转[N]，用于[Y]。动词只有两个【推断】：换（对交易池，条件组合器预填标准组合「凭证∧双方确认」，可调）与转（对联系人，条件从空集起步自由组合）——条件是所有支付共有的槽位（组合模型见本节下方），不是一类单独的订单 | §8.3、§9.1 第 1 步 | 已做 |
| 5 | 核对 | 自然语言单必经可编辑核对卡：推断项（虚线）逐项确认后才可提交；配对不存在、低于最小额等阻断项都在卡内解决，提交后不再出现第二问【决策】 | 本节新增 | 已做 |
| 6 | 支付确认 | **每一笔都出收银台、每一笔都过 Passkey**（详见 §9.4）。金额分档不再决定「要不要确认」，只决定是否额外提示超限原因：敞口超过「用户阈值 × 对手方兑现率放宽系数（§10.6）」时，收银台上多一行琥珀色说明 | 本节新增 | 已做 |
| 7 | 执行与终态 | 托管 → 条件判定 → **放行共识**（§9.1 第 6 步）→ 放款或原路退回，全程展示资金所处站点与预计时间。四种终态语义互斥【决策】：完成（回写履约）/ 撤销（成交前退出，非违约，不回写）/ 超时（违约，负向回写）/ 异议（升级 L2，资金锁定至裁决） | §9.1 第 4–6 步；终态语义为本节新增 | 已做 |
| 8 | 回写与历史 | 履约结果回写对手方兑现率，进而影响其单笔上限与放行时的信任分（与第 6 环节、§9.1 第 6c 构成闭环）；单据包沉淀为历史订单，工单终态后只读，一单一工单 | §9.1 第 7 步、§10.6 | 已做（History 页，2026-08-24 改为台账式：日期分组、金额右对齐成列、状态筛选） |

V1 条件库只收当期真实可裁决的三类依据：本人确认、对方凭证 + 沉默窗口、时钟【决策 2026-08-19】。物流 API、价格源等 L1 依据到 Phase 2 接入后再进库——能力没到的条件不出现在承诺环节。

「条件」一词须区分两类【决策 2026-08-21】：**触发条件**（何时下这个单——定时、到价、事件触发，属交易执行层，V1 不做）与**释放条件**（资金入托管后何时放给对方——条件库全部属此类）。界面词根统一用 Release condition，不用 When——"When + 日期"会被读成"到期才下单"，两笔完全不同的交易。

**释放条件 = 原子条件的组合**【决策 2026-08-21】：条件不是单选模板，是最多三个原子条件的 AND 组合——全部满足才释放；**什么都不选（空集）= 立即释放**，Immediately 不是特殊成员。OR 不做：「任一满足即放」意味着对手方只需攻击最弱条件。

| 原子 | 判定者 | 参数 | 状态 |
|---|---|---|---|
| 确认 Approval | 人的意思表示 | **「谁确认」下拉：双方确认（默认）/ 我确认**【决策 2026-08-24，取代 2026-08-21「恒为双方」口径】。依据：单方场景真实存在（我验收即放款，不需要对方再点一次），锁死为双方等于让用户为不存在的对手动作等待 | 已上线 |
| 凭证 Evidence | AI 验人上传的文件 | 凭证类型（银行回执/交割单/工作成果） | 已上线 |
| 数据 Data | AI 读客观数据源 | **三段联动**：数据源 → 指标（随数据源变）→ 目标值（自由输入，如 ≥ 1,000）。演示数据源：广告平台 / 物流 / 支付网关 / 链上预言机 | 已上线（原型；真实数据源接入与预言机责任） |
| 时间 Time | 时钟 | 绝对日期 / 相对天数 | 已上线 |

三条配套规则【决策】：

1. **时间的双重角色拆开**：作为释放条件（AND 成员，「到 9/1 ∧ 双方确认」= 都确认了 9/1 前也不放）与作为**超时兜底**（每个非空组合必填的失败路径：「N 天未走完 → 升级审查」）是两个字段，不混进条件集。
   **2026-08-24 补充**：超时兜底也**不写进条件文本**。此前回执里拼成「…· unresolved after 14 days goes to review」，既读不懂（"unresolved" 指谁没解决），又把一个用户从未在编辑器里选过的值当成他设的条件念给他听。现在条件行只写条件本身，兜底压一档小字单独说明，且只在单子还可能悬着时出现（放款/撤单后消失）。
4. **条件类型 ≠ 编译主分支**【决策 2026-08-24】：组合会被编译成托管状态机的四条主分支之一（Immediately / When I confirm / Proof + window / On a date），这是内部实现；**但轨道站名与文案必须跟真实条件类型走**。此前 API 数据条件被编译到 On a date，界面就跟着说「Waiting for the date」——它等的是指标不是日子。真实类型随单据一路带下去，不从编译结果反推。
2. **AI 放行共识不进条件集**：它是恒定流程（条件集全满足后、动钱前，§9.1 第 6 步），与条件组合正交。
3. **OTC 不是特例**：Buy/Sell 与条件单共用同一个组合器，区别只是**默认值**——OTC 预填标准组合「凭证(银行回执) ∧ 双方确认」，用户可调【决策 2026-08-21，取代此前「协议锁死」口径】；条件单从空集（立即）起步。卖单另有独立的付款时限兜底（未付 → 撤单解锁）。

场景覆盖验证：普通转账=∅；OTC=凭证∧对方确认（兜底：付款时限未付→撤单）；定制采购=双方确认（14 天→审查）；广告结算=数据(点击≥X)∧双方确认（投放期+7 天→审查）；工资房租=时间(每月 1 日)；里程碑=凭证∧我方确认∧时间(不早于 M 日)。


**卖方（商户）支线**：交易池里的单从哪来。三层递进，层级不能揉在一起【决策 2026-08-21】：

1. 账户级 · KYC/KYB（第 1 环节，一次）
2. 能力级 · 挂单配置：方向 / 币种 / 单笔限额 / 网络 / 法币轨道，提交后人工审核放行（一次，改配置重审）
3. 单笔级 · 挂单：本次卖多少、什么价、最小单——选项范围由能力配置圈定，**卖单挂出即锁币**（买家看到的 Size 必须真的锁在托管里），走 Passkey 强确认；下架即解锁。新商户无历史，履约数据从零累计，不预填。

### 9.1 通用条件支付流程（第 1–2、5–7 步原型已实现；第 3 步押金/费率定价未实现）

1. 提交订单：金额、对手方、释放条件。
   **核对卡**：自然语言解析出的订单在提交前先出一张核对卡，被推断（而非用户明说）的槽位标虚线；有虚线未确认就点提交，只把问题标在问题上（变色、抖动），不弹解释。同时在这一步拦掉撮合层面必然失败的单（该币种/法币无对手方、低于最小单），并就地给出可选替代，不把用户放到下一步再失败。
   依据：解析必然有猜的成分，把「哪里是猜的」显式标出来，比事后追责便宜；而"提交后才发现没人接"是最贵的一种失败。

2. 双向验资 = **多 agent 共识**【决策 2026-08-21】：每个 agent 只看一个维度、只用一路数据（身份、资金溯源、地址聚类、制裁名单、履约行为、报价偏离、频次异常），独立出票。

   **门槛用票数不用百分比**【决策 2026-08-24，取代原「同意率 ≥90%」】：当前为 **7 票中 6 票**。依据：百分比阈值与信任分同为「90」，同屏出现时无法分辨哪个是哪个；票数是离散事实，也更接近共识本身的含义。

   **2a 证据层**【2026-08-24 补】：票不是结论，票要能被复核。每个 agent 附一份底稿，四段固定结构：

   | 段 | 内容 |
   |---|---|
   | 查了哪儿 | 数据源清单 + 各自的查询时间戳 |
   | 查到什么 | 关键字段的实测值 |
   | 跑了什么校验 | 逐项校验及其结果（如人证比对 92%、剥离链模式未检出） |
   | 原始记录 | 抄回来的原文摘录（交易哈希、接口响应、名单查询串与被拒的最高相似项） |

   资金溯源那一票的底稿是**资金链路本身**（几跳、每跳的标签与金额、混币器/跨链桥暴露度），不是键值对。带 note 的票（如频次异常）必须把触发它的那几个数字摆出来，而不是只说"有点异常"。
   依据：用户是本金持有方，他信的不是动画是能被查证的东西；"AI 说没问题"和"AI 查了这些、结果是这些"是两个产品。
3. 信用模型输出该笔的押金比例与费率
4. 资金进入托管
5. 条件判定，证据分三级：L0 双方确认 → L1 客观数据源（物流、回执、链上事件）→ L2 争议裁决
6. **放行共识**【决策 2026-08-21，2026-08-24 扩写】：条件成立后、动钱之前，agents 对「是否照双方同意的合约执行」再共识一次。边界不变：此步**无裁量权**，只能「放行」或「拦下转人工」，不能改判条件——否则「条件成立即放款」的确定性被打破。

   **6a 票型（三票 → 五票）**：三票常驻 + 两票随条件类型换人，谁去读那份证据谁就出票。

   | 票 | 出票方 | 读什么 |
   |---|---|---|
   | 常驻 | Terms | 金额 / 收款方 / 用途对签署后的合约，有无签署后修改 |
   | 常驻 | Custody | 资金是否仍锁在本托管、有无被重复占用 |
   | 常驻 | Screening | 放款地址、制裁名单（放款这一刻重查）、是否仍在授权卡额度内 |
   | 条件 = 凭证 | Document + Match | 发行方签名 / 有无重编码涂改 / 是否旧件重传；金额、付款方、收款方、日期逐项对单 |
   | 条件 = 双方确认 | Approval + Delivery | 两侧 passkey 签名、有无重放旧授权；交付物哈希在确认后有无被换 |
   | 条件 = API 数据 | Oracle + Source | 取指标并间隔复读一次防瞬时值；响应签名、账户绑定、有无 sandbox 标记 |
   | 条件 = 时间 | Clock + Schedule | 多时间源一致性、时区、有无回拨；有无延期请求或修订 |

   **6b 放行闸门（AND 语义）**【决策 2026-08-24】：放行不是一个判断，是一组判断的**合取**——用户设的每个条件原子各算一条，外加平台侧一条「放款这一刻对手方的信任分」。**任一条不成立即不放行**。界面上每条都摊开写「实测值 vs 阈值」（如 `Clicks 1,247 / 需 ≥ 1,000`、`信任分 91 / 需 ≥ 85`），而不是只给一个通过与否。
   依据：条件支付的卖点是确定性，而确定性只有在「凭什么放」可被逐条复核时才成立；给一个总分等于把黑箱换了个位置。

   **6c 信任分门槛**：当前取 **85**（与「85 以上按低风险定价」同一口径）。**是否随金额浮动、未过时是暂缓 / 转人工 / 部分放行，均未定。**
7. 条件成立放款并出具单据包；不成立原路退回
8. 履约结果回写信用记录

| 2 | 双向验资 | A | B |
| 3 | 撮合成交 | A | B |
| 4 | B 转 U 入托管，二次筛查 | A | 托管 |

三个设计要点：

2. 第 6 步的放款依据是银行凭证，不是 B 的确认意愿
3. 双盲：双方全程不知道对方身份，兼作安全机制与防绕单机制

要点：`s3` 的付款窗口逾期即判违约（与「撤销」区分，见 §9.0 四种终态）；`s5` 完成后履约结果回写对手方兑现率。买方在 `match` 与 `s3` 两态可主动撤单，撤单记为未成交而非违约。

### 9.3 资金链路

> 回答：资金怎么进来、在哪里、怎么出去，我们在每一步是什么角色。

三种资金形态各走各的链路：

| 形态 | 谁保管 | 我们的角色 |
|---|---|---|
| 数字资产（USDT / USDC 等） | Atara 托管账户（持牌主体） | 保管 + 判定 + 记账 |
| 法币 | 用户自有银行账户 / 持牌合作方 | 只核验凭证，不在资金路径 |
| AIUSD | 非资金形态，是记账单位 | 额度、条件、押金的计价 |

托管资产与「不当交易对手方」不冲突：托管是代客保管，后者指不用自有资产负债表接单，两者并存。

**数字资产六步**：

| # | 步骤 | 资产位置 | 我们做什么 |
|---|---|---|---|
| 1 | 入金 | 用户钱包 → 专属充值地址 | 生成地址、监听到账、溯源与地址聚类筛查 |
| 2 | 可用余额 | 托管账户，记在用户名下 | 记账；受支付规则约束 |
| 3 | 进入条件托管 | 同上，标记为该笔专用 | 双方均不可动用；持判定权不持处分权，放款只能按预先写定的条件执行 |
| 4 | 判定 | 托管中 | L0 → L1 → L2 |
| 5 | 出口 | 成立→收款方；不成立→原路退回 | 执行、出具单据包、回写信用 |
| 6 | 出金 | → 用户白名单地址 | 白名单校验（登记后延时生效）、双因子、出金筛查 |

第 1 步筛查未通过的资金隔离并转入补充材料流程，不直接退回【决策】——退回本身可能构成资金链路的一环。

**法币链路（OTC）**：买方银行账户 →（点对点）→ 卖方银行账户。我们只接收买方上传的回执，核验通过后触发数字资产腿放款，全程不持有、不代收、不代付。

**托管账户与连钱包**：Phase 1 采用托管账户【决策】。依据：托管 / 支付牌照路径已定；无智能合约的资产只能账户托管；法币凭证核验与放款联动需要账户体系承载。连钱包（资产不离开用户钱包，以链上授权在条件成立时划转）列为后续选项，适合纯链上条件，但覆盖不了法币腿。两种模式是否并存，按阶段推进。

**原型实现的出入金向导**（2026-08-24 回填）：

- **入金**：先选链（同一币种多链并存，如 USDT 走 TRON / ETH），再给该链的专属地址；跨链错转不可找回的告警与地址同屏，不放进帮助文档。
- **出金四步**：`地址 → 金额 → 用途 → 证明文件`。用途为受限选项（OTC 结算 / 货款 / 服务费 / 退款 / 内部划转 / 其他），大额或特定用途要求上传证明。
  依据：出金是唯一资金离开体系的口子，用途与证明在这一步收集，成本最低、举证最完整；事后补材料等于事后重建事实。
- **收款人管理**：银行账户与链上地址分两类维护，各自带币种/网络与关系标注（本人 / 对手方）。银行账户按地区分组（原型覆盖 5 个地区、22 条法币通道）。

**计价口径**：当前额度与条件按 AIUSD 记账（1 AIUSD ≈ 1 USD），界面折算显示。冲突点：对话前台的既有示例为人民币计价的条件支付，若要直接以人民币计价并托管，须由持牌合作方提供法币账户，与「法币不经手」的边界须一并设计。

### 9.4 支付确认与会话安全

> 决策日期 2026-08-24。回答：钱要动之前，用户看到什么、要过几道。

**收银台（每一笔都出）**：动钱的每一笔——条件单、交易池成交、挂卖锁币——都先出同一张支付确认面板。此前只有超对手方限额那一档才弹，导致多数转账无任何确认就离开账户。
面板自上而下只答三件事：

| 位置 | 内容 | 为什么在这 |
|---|---|---|
| 主位 | 大字金额，币种符号与数字同级 | 付多少是唯一不能看错的信息 |
| 中位 | **授权卡**（额度窗口）：周期已用 / 上限、单笔上限、收款白名单，并把本笔占掉的额度画在进度条上；超单笔上限时标 over cap | 卡在我们的模型里就是一个额度窗口（§10.5），不是带卡号的银行卡。这一屏是它唯一需要出场的地方 |
| 中位下 | 资金实际去向的**陈述句**（法币：从你名下哪个账户直付卖家、币种不符时由你的银行换汇；数字资产：从可用余额锁进托管） | 法币不进平台是硬边界，最该在动钱这一刻讲清楚。它是事实不是选项，所以不做成选择器 |
| 底部 | Confirm with passkey | 见下 |

**认证：每笔 Passkey，不分档**【决策 2026-08-24】。原设计按金额三档（自动 / 一键 / 强确认），已取消。
依据：分档要成立，前提是"小额出错可承受"；但条件支付的用户是本金持有方，小额同样是本金，且分档线本身难以给出有依据的取值。

**支付密码退出支付流程**【决策 2026-08-24】：支付密码不在收银台出现。它的定位是**没有 Passkey 时的退路**，以及**解锁会话**。
依据：付款默认走 Passkey；在 Passkey 之外再叠一道密码，等于告诉用户前一道没有意义。

**取消 30 秒后悔窗口**【决策 2026-08-24】：原设计在托管建立后给 30 秒无理由撤销。取消。
依据：确认环节已经过 Passkey，再给一个倒计时是自相矛盾——它在说那道认证可以不算数。真正的可逆性放在它该在的地方：**条件成立之前，撤单入口（Cancel order）一直在**，撤单原路退回、不记违约。这与 §9.0 四种终态语义一致，且比一个计时器诚实。

**会话锁**【决策 2026-08-24】：闲置 15 分钟自动落锁，整屏重虚化（看得见有内容、读不出内容），用支付密码解锁；落锁同时把余额重新遮回。
依据：控制台上摊着余额、对手方和单据，多数用户在共用屏幕前使用，与「余额默认隐藏」同一条理由。解锁不设任何模仿真实凭据的输入——与 Passkey 仪式同一条纪律。

### 9.5 交易大厅与挂单（原型已实现，2026-08-24 回填）

> 回答：一笔 OTC 在撮合之前，双方各自看到什么、能做什么。

**买方侧 · 大厅**。列表按买/卖分侧，可按币种与法币筛选。每条挂单摊开的信息决定了这个市场是不是"信用可定价"：

| 字段 | 为什么在列表上而不是详情里 |
|---|---|
| 信任分、成交笔数、纠纷数、履约率 | 选谁交易的判断依据，藏进详情等于逼人盲选 |
| 资质文件徽标（KYC / PoF / 对账单 / 地址证明 / 资金来源 / 链上） | 缺哪张一眼可见；点开可查看该件 |
| 单价、可成交量、最小单 | 最小单决定这条单跟自己有没有关系 |
| 中位放行时长 | 履约速度是履约质量的一部分 |
| 结算法币与可用网络 | 币种/网络不匹配的单不该浪费点击 |

**场景分区**：大厅顶部按结算场景分区，OTC 池已上线；「算力与 API」（按调用结算）、「商户」（验收后付款）为规划中，灰态展示并写明各自的对手方特征、条件与证据来源。
依据：条件支付不是只有 OTC 一种形态，分区把"同一套条件模型能覆盖哪些场景"变成产品上可见的事实，而不是文档里的说法。

**卖方侧 · 挂单**（三层结构见 §9.0）：挂单弹窗按当时汇率预填价格与点差，收款通道按地区分组多选；**卖单挂出即锁币**，锁的量就是买方看到的量；下架即解锁。

### 9.6 资质与文档中心（原型已实现）

六类资质件：`KYC / 资金证明 PoF / 银行对账单 / 地址证明 PoA / 资金来源 SoW / 链上地址证明`。每件有独立状态，双方在成交前后都可查看对方已提交的件。
两个设计要点：

1. **资质是分项而非一个"已认证"布尔值**。不同金额、不同场景要求的件不同（如大额要 PoF 与 SoW），合并成一个开关等于放弃了风险定价的粒度。
2. **缺件是公开信息**。挂单上直接显示哪几件没有，让买方自己定价这个缺口，而不是由平台代为过滤。

### 9.7 定时付款与授权卡的运行时（原型已实现）

授权卡（§10.5）在运行时的两种形态：

- **单笔支付**：作为额度窗口出现在支付确认面板上（§9.4），本笔占掉的额度画在进度条上，超单笔上限即时标出。
- **定时付款**：按周期自动发起（房租、月度 API 预算、订阅等），下次执行时间与金额常驻账户页。托管窗口内可撤销。

定时付款失败（余额不足 / 超限 / 对手方状态变化）的处置按「转人工确认」设计。

## 10. 接入方式（人与 agent）

> 回答：人和 agent 各自怎么把这套能力用起来，各自能做什么、不能做什么。

### 10.1 一套协议，两类发起方

不为 agent 单独设计一套 API 语义：协议是什么结构，界面就是什么结构【决策】。人这边是自然语言绑定到结构化句子，agent 那边是同一 schema 的协议字段。由此 agent 发起的付款可直接渲染成同一句话给人看，升档到强确认时不需要另做一套确认界面。

| | 人 | agent |
|---|---|---|
| 入口 | 对话前台 / 控制台 | 协议端点（同一 schema） |
| 身份 | KYC / KYB | 从属于已认证主体的授权；作为对手方时为独立主体 |
| 认证 | Passkey（每笔）+ 双因子；支付密码为无 Passkey 时的退路，见 §9.4 | 授权码 + 签名 |
| 可支配 | 全部可用余额，受自设规则约束 | 被授予的子额度 |

### 10.2 Agent 的两种角色

两种角色的资金来源与信用归属不同，必须分开处理：

| 角色 | 关系 | 用谁的资金 | 信用记在谁身上 |
|---|---|---|---|
| 代理 | 从属于某个已认证主体 | 该主体的可用余额，受其设定的额度约束 | 主体，同时累计该 agent 自身的兑现率 |
| 对手方 | 独立主体 | 自己的账户 | 自己的信用记录 |

同一 agent 可同时具备两种角色（代表 A 去购买 B 提供的服务）。agent 不设独立钱包：授予的额度是对主体可用余额的支配权，不是另一个账户【决策】。依据：独立钱包需预先划转，资金闲置且出错时敞口为钱包全额；额度模式下资金始终在主体名下，可随时调整或撤回，与三档授权、可撤销的既有设计一致。

额度为上限而非预留【决策】：不锁定对应金额，代价是余额不足时支付失败并转为待人确认。依据：预留造成资金闲置，与「押金只压到实测风险大小」的定位冲突。

### 10.3 接入流程

| # | 谁 | 做什么 |
|---|---|---|
| 1 | 人 | 创建 agent 授权：周额度、单笔上限、对手方白名单、允许的条件模板 |
| 2 | 系统 | 签发授权码与协议端点，权限即创建时所设 |
| 3 | agent | 用同一套结构化 schema 下条件单 |
| 4 | 系统 | 判档：额度内且白名单内直接执行；越界退回为待人确认，并渲染成同一句话 |
| 5 | 系统 | 执行结果回写该 agent 的兑现率，影响其后续授权档位与托管窗口长度 |

### 10.4 接入形态

三种并列，对应 agent 的不同运行环境：

```
claude mcp add --transport http atara https://mcp.atara.xyz --header "X-Atara-Key: <授权码>"
npx skills add atara/pay
npm i @atara/sdk   /   pip install atara
```

装载后 agent 获得的工具，与人在控制台可执行的动作一一对应：

| 工具 | 作用 | 约束 |
|---|---|---|
| `check_counterparty` | 查对手方风险分、履约记录、争议历史 | 只读 |
| `create_conditional_payment` | 下条件单 | 超额度或白名单外 → 退回为待人确认 |
| `get_status` | 查某笔状态与判定进度 | 只读 |
| `dispute` | 不提供 | 异议只能由人提出 |

### 10.5 授权卡：人与 agent 用同一种对象

人自己的支付规则与给 agent 的额度是同一种东西——都是主账户上的一份支配权，因此用同一个对象表达：**一个账户，若干张授权卡**【决策】。人自己是一张卡，每个 agent 各是一张。

判断依据：两者的机制完全相同（额度、单笔上限、时间窗口、越界转人工），若分成两套概念，用户需要理解两次，且新增 agent 时无处安放。信用卡是已有的成熟心智——卡不是钱包，是账户上的支配权，可停可改可换额度。

一张卡的属性：

| 属性 | 说明 |
|---|---|
| 周期额度 | 每周 / 每月上限，与已用量 |
| 单笔上限 | 超过转强确认 |
| 时间窗口 | 窗口外一律需确认 |
| 可付给 | 对手方白名单 |
| **允许的条件** | 限定该卡能用哪些条件模板（如只允许「等交付」，不允许「立即」） |
| 兑现率 | 该卡的历史履约表现，影响其可获得的授权档位 |
| 状态 | 启用 / 停用 |

「允许的条件」是这套模型相对普通信用卡多出的一档：普通卡只能限额度与商户类别，这里可以限定**用什么条件付款**，把风险控制写进授权本身而不是事后审计【推断】。

### 10.6 兑现率的信号来源：声明在发卡时，不在每笔付款

> 回答：授权卡的「兑现率」这个数，具体由什么产生。

**结论**：兑现率度量的是**授权卡被使用的方式，与发卡时声明的授权范围之间的偏离**，而不是每笔付款附带的用途标签【决策】。

#### 判断依据一：能被系统挡住的规则不产生信用信息

授权卡的额度、单笔上限、白名单属于硬约束，命中即当场拦截或转人工（见 10.7）。被拦截的行为没有发生，因此不构成对持卡方的观察【推断】。若信用分只由这类规则产生，其信息量等同于静态限额——同类做法在 Kite 与 AP2 上已存在，其限额与对手方无关，不随履约表现变化【事实，来源 `COMPETITORS.md` §2.1】。

#### 判断依据二：可产生信号的声明需同时满足四个条件

| 条件 | 说明 |
|---|---|
| 事前做出 | 结果尚未发生时给出 |
| 可能为假 | 存在与实际不符的可能 |
| 事后可判定 | 有确定的比对对象 |
| 声明者有含糊动机 | 含糊对声明者有利，否则声明无成本也无信息 |

以此检验常见的用途标签（房租、采购尾款、服务订阅）：这类标签在付款完成时即为真，不存在「未兑现」状态，第二、三条不成立【推断】。另一类标签（交付验收）四条均成立，但它描述的是放款条件，已由条件槽表达，重复记录不增加信息。

「这笔用了哪张卡」同样不满足第二条：卡的归属是系统可直接观测的事实，不是声明。

#### 判断依据三：发卡时的声明满足四条

发卡时声明的内容为：该卡可付给谁、单笔与周期上限、允许使用哪些条件模板。这是对未来行为范围的陈述，可能与实际不符，且持卡方有把范围写宽的动机。

#### 由此确定的三类信号

| 信号 | 观测对象 | 为什么硬约束覆盖不到 |
|---|---|---|
| 越权申请 | 超出单笔或周期上限而转人工的频次，及人工审核的通过率 | 卡允许申请超额（见 10.5「越界转人工」），申请本身是行为，不是被拦截的事件 |
| 条件到期兑现 | 该卡使用的条件模板在到期时的兑现比例 | 条件是否成立在付款时不可知，只在到期后确定 |
| 额度声明与实际用量的偏离 | 声明额度与实际使用量的长期差 | 长期远低于声明额度，说明该声明不含信息；长期顶格且频繁申请超额，说明声明范围与实际不符 |

三类均为事后可判定，且与硬约束不重叠【推断】。

#### 适用边界

| 发起方 | 是否适用 | 依据 |
|---|---|---|
| agent | 适用 | agent 的全部行为由授权卡界定，「是否待在声明范围内」是其可跨平台携带的核心记录。同类记录在现有 agent 支付协议中未见提供【事实，见 10.8】 |
| 企业用户（人） | 有限适用 | 人同样有常设规则，但人对每笔付款可逐笔确认，声明与实际的偏离空间较小，信号强度低于 agent【推断】 |
| 个人消费用户 | 暂不适用 | 个人小额支付通常不存在事先声明的授权范围，也没有需要放宽的管制。要求其申报用途会产生披露成本而无对应收益【推断】 |

#### 含义

授权卡本身是执行层，兑现率是定价层。仅有授权卡时，该模型与既有的 agent 策略引擎无实质差别；兑现率回写额度与托管窗口（见 10.5）后，授权范围才随履约表现变化【推断】。

### 10.7 能力边界

| 能力 | 人 | agent |
|---|---|---|
| 发起支付 | 可 | 可（额度与白名单内） |
| 改规则、额度、白名单 | 可 | 不可 |
| 强确认档放行 | 可 | 不可，退回给人 |
| 登记新收款地址 | 可（延时生效 + 双因子） | 不可 |
| 提出异议、接受裁决 | 可 | 不可 |
| 完成 KYC / KYB | 必须本人 | 不适用 |
| 托管窗口内撤回 | 可撤任意一笔，含 agent 发起的 | 仅可撤自己发起的 |

三条安全边界：

1. agent 不能扩大自身权限，所有权限变更回到人。这是授权模型成立的前提。
2. 越界不是报错而是转人工——超额、新对手方、白名单外地址，任一命中即退回为待确认，不丢弃、不静默失败。
3. 托管窗口内人始终可撤回 agent 的操作。

### 10.8 与既有 agent 支付协议的关系

现有协议解决的是「怎么付」。Tempo Machine Payments Protocol（2026-03 上线）以 HTTP 402 为基础，定义 Charge / Session / Subscription 三种支付意图，其中 Session 允许 agent 一次授权消费上限后在通道内流式付款；x402（Coinbase 发起，现由 Linux Foundation 托管）为同类机制。两者均未覆盖对手方风险判定与履约保障——对 Tempo 官方文档与 MPP 协议规范全文检索，risk / escrow / dispute / collateral / counterparty 均无出现【事实，2026-08-14 核实，来源 mpp.dev/protocol、tempo.xyz/docs】。MPP 规范要求客户端在授权前自行核实「收款方是否符合预期」，但未提供判断依据。

据此定位为这些协议之上的风险层，不另造支付协议【决策】：

| 层 | 内容 | 目的 |
|---|---|---|
| 兼容 | 支持 402 challenge 流程，作为其一种支付意图 | 已接入上述协议的 agent 不改代码即可使用 |
| 增量 | 在 challenge 响应中附加对手方风险分与建议押金 | 补上规范要求 agent 自行判断却未提供依据的环节 |
| 独有 | 条件支付与争议裁决 | 即时结算协议不提供的能力 |

## 11. 规则与边界

> 回答：哪些事我们做，哪些事在任何情况下不做。

1. **不当交易对手方**。裁决方不在被裁决的交易中持有头寸，不用自有资产负债表接单。原因：裁决方若能从判决结果获利，判定的中立性不成立。
2. **发行与裁决分离**。AIUSD 发行主体与裁决主体为两个法人。原因：监管禁止稳定币付息，发行侧收益为零，全部收入来自条件层，两种业务的监管要求不同。
3. **两池资金隔离**。稳定币储备池与赔付准备金池法律隔离，不得互用。原因：用储备资产吸收赔付损失是多次储备型资产失败案例的共同原因。
4. **法币不经手**。OTC 业务中法币点对点走银行，我们不在资金路径中。

**报价口径**：现阶段所有方案收取服务费而非承保费——不承担损失，只保证判定错误时资金退回。

**新场景筛选标准**（四问）：释放条件能否客观验证；履约数据能否用于信用模型；违约损失是否大到用户愿意付费；争议笔数是否足够积累判例。前两问是准入条件，后两问分别筛选出大额市场与高频判例市场，两条线并行。

## 12. 异常情况

> 回答：每个环节出错时如何处理。

| 情况 | 处理 | 依据 |
|---|---|---|
| 验资不通过 | 不进入撮合 | 核验结果 |
| 撮合后一方反悔 | 记录违约，后续交易提高保证金 | 成交确认 |
| U 已入托管，A 不打款 | U 原路退回 B | 成交窗口超时 |
| 托管资金二次筛查不过 | 原路退回，交易取消 | 筛查报告 |
| A 已打款，B 拒绝确认 | 凭银行回执放款给 A，不需要 B 同意 | 银行凭证 |
| 条件证据冲突或无数据源 | 升级至争议裁决（L2），输出可解释的裁决结果 | 裁决规则 |

倒数第二行是托管设计成立的关键：资产在托管方手中，才能在一方恶意不配合时保护另一方。

## 13. 成功指标

> 回答：怎么判断这个产品做成了。

| 指标 | 说明 |
|---|---|
| 年化条件支付总金额 | 主指标 |
| 判定记录数 | 第一阶段目标：累计 10,000 笔以上（信用模型可用性的前提） |
| 争议率 / 裁决被接受率 | 裁决质量：进入争议的比例，及当事人不再上诉的比例 |
| 资金占用下降幅度 | 相对全额托管，信用定价为用户释放了多少资金 |
